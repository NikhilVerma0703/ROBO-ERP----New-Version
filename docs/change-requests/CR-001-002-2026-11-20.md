# CR-001 and CR-002: the first changes to standalone Robo ERP (20 Nov 2026)

These are the two existing ERP bugs found during Phase 4 verification (`docs/VERIFICATION-REPORT.md` §4). Both are **implemented and verified**. They are the first places where this project's code differs from the main ERP's Robo module.

## CR-001: re-importing an export lost the machine setup of Shift B/C slabs

**Before.** The Complete Production download writes its Production Setup sheet without a Shift column. The importer filed every setup row under shift 1. A Shift B or C slab line therefore matched no setup row, and it was attached to a new setup with **no machines, no production date and no target slabs**.

**Now:**
- A setup sheet with **no Shift column** applies to every shift of its date and design. Rows filed under the slab's own shift still win when a sheet has them.
- A sheet that **has** a Shift column is read exactly as before, including a blank cell meaning shift 1.
- A setup the import creates now gets its **Production Date** (the run's date) and its **Target Slabs** (read from the sheet's "Target Slabs" column).
- The two-batches-of-one-design rule (E2E-24) is unchanged.

**Files changed:**
- `src/lib/robo/registerSetups.ts`: added `ANY_SHIFT`, `setupShiftOf`, `setupEntriesFor` and `setupTargetSlabs`. `soleSetupDesign` now counts shift-less rows for every shift.
- `src/lib/robo/importRegister.ts`: added the "Target Slabs" alias; files setup rows by `setupShiftOf`.
- `src/app/api/robo/imports/route.ts`: uses `setupEntriesFor`; sets `productionDate` and `targetSlabs` on the setup it creates.

**Verified** on a fresh local database. A Shift C batch (D-9002, 4 machines, target 5) was exported, its slabs deleted, and the export re-imported. The result was "Imported 5", and the new setup had date 2026-11-21, target 5 and **4 machines** (before the fix: none, none, 0). The re-exported slab rows are identical. The setup rows are identical in every machine value; only Notes differs, because imported setups are labelled "Imported from production register" (unchanged ERP behaviour).

## CR-002: a duplicate name in a master list returned HTTP 500

**Before.** `POST /api/robo/{tools,liquids,powders,designs,programs}` passed the name straight to the database. A name already on the list failed on the unique index and came back as an HTTP 500. The Master Lists screens ignored the answer, so nothing was shown. Delay Codes was the only list that already refused duplicates properly.

**Now:**
- A name already on the list is refused with **409**, for example `A tool named "BOAT 120" already exists.` This is checked before the create, and also caught if two people add the same name at the same moment.
- Names are trimmed.
- An empty name is refused with 400.
- A program must name an existing design (400, `Pick the design this program belongs to.`; before, this was a 500 too).
- The Tools, Liquids, Powders, Designs and Programs screens now show the message and keep what was typed.
- The Robo Entry form's "+ Add" in the comboboxes is unchanged: it already treated any refusal as a failed add.

**Files changed:**
- `src/lib/robo/masterNames.ts` (new).
- The five `src/app/api/robo/*/route.ts` POST handlers.
- `src/components/robo/masters/{SimpleListMaster,DesignsMaster,ProgramsMaster}.tsx`.

**Verified:**
- Duplicate tool, liquid, powder, design and program each returned 409 with their sentence.
- A padded duplicate (`"  BOAT 120  "`) returned 409.
- An empty name returned 400, a program with an unknown design returned 400, and a new name returned 201.
- On the Tools screen, adding "BOAT 120" showed `A tool named "BOAT 120" already exists.` with the name kept in the box.
